## Tables

### notifications

Stores the history of activity and warning notifications generated by Hatchery. Consumed by the notification tray, toast overlay, and Notifications pane.

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `id` | `INTEGER` | `PRIMARY KEY AUTOINCREMENT` | Auto-assigned |
| `created_at` | `TEXT` | `NOT NULL` | ISO 8601 timestamp (UTC) |
| `tier` | `TEXT` | `NOT NULL` | `warning` or `activity` |
| `message` | `TEXT` | `NOT NULL` | Human-readable description of the event |
| `resolved` | `INTEGER` | `NOT NULL DEFAULT 0` | `0` / `1` — warnings only; set to `1` when the condition clears |
| `dismissed` | `INTEGER` | `NOT NULL DEFAULT 0` | `0` / `1` — set to `1` when dismissed by the user |

#### Tiers

| Tier | Behaviour |
|---|---|
| `warning` | Persistent condition requiring attention (e.g. missing system requirement). Cleared by the system when the condition resolves — not by user dismissal. |
| `activity` | Timestamped record of a user action or system event (e.g. "Clutch exported", "VM hatching started"). Informational; dismissed by the user. |

#### Managed by

`lib/notifications.py` — `record()`, `list_recent()`, `resolve()`, `dismiss()`

### clutch_instances

Tracks observed runtime state of VMs hatched from Clutch definitions. Associates each running VM with the Clutch that defined it, enabling instance-aware reconciliation.

## Maintenance

### Row cap

The `notifications` table is capped at **500 rows**. On every insert, `lib/db.trim_notifications()` deletes the oldest rows beyond the cap. This runs automatically — no manual maintenance required.

The cap is defined as `_MAX_NOTIFICATIONS = 500` in `lib/db.py`.

### Migrations

The current schema uses `CREATE TABLE IF NOT EXISTS`, which is idempotent and safe to run on every startup. It cannot alter existing tables.

When a future change requires adding or modifying columns, the approach will be:

1. Add a `schema_version` table to track applied migrations
2. Apply `ALTER TABLE` statements on startup when the version is behind
3. Bump the version after each migration

No migration infrastructure is needed yet. This is the documented plan for when it becomes necessary.
